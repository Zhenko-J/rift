# Couverture rvt-mcp et pyRevit MCP — sort de chaque outil non repris

**Proposition du 2026-10-13.** Approuvé le 2026-10-13 : le sort par domaine, R2 (`place_family` écarté), R3 (prompts et ressource au registre), R7 (pas de hook client pour RIFT) → ADR-030. **Reste à arbitrer** : les 26 outils « à arbitrer » (RIFT ou NORN FORGE / PRESS) et le prompt `revit_drawing_layout`. Source : l'inventaire du poste du 2026-10-13 (`tools/list` JSON-RPC sur rvt-mcp 1.1.0 et sur l'extension pyRevit MCP), tenu par la suite NORN hors de ce dépôt ; registre RIFT au commit `8863b6f` (79 outils, 4 livrés).

## Constat

- rvt-mcp expose **233 outils** : **66** sont cités comme origine par un `ToolSpec` RIFT, **167** ne le sont pas. Toutes les origines citées existent bien dans les serveurs réels.
- pyRevit MCP expose **20 outils** : **19** cités ; `place_family` non repris.
- rvt-mcp expose aussi **6 prompts** (`revit_getting_started`, `revit_pre_issue_check`, `revit_model_audit`, `revit_drawing_layout`, `revit_stairs`, `revit_change`) et **1 ressource** (`Session Context`) que le registre ne sait pas représenter.
- Les familles MEP, structure, liens, pièces, annotation, géométrie et création d'éléments ne sont **pas** sans décision : **ADR-027 §4** les écarte déjà (« tools nobody uses on the maintainer's workstation (element creation, rooms, annotation, links, geometry, structure, MEP) stay out of the catalogue until an issue asks for them »). Ce qui manquait, c'est le rattachement outil par outil, fait ci-dessous.

| R3 | prompts et ressource rvt-mcp | Ajouter au registre un type `PromptSpec` (nom, vague, origine, statut) et `ResourceSpec`, générés dans le catalogue comme les outils ; inscrire `revit_change` (M2 : il porte la discipline survey → accord → `record_change`, ADR-026 §2), `revit_model_audit` et `revit_pre_issue_check` (M3, avec `audit_model`), `revit_getting_started` (M4), `revit_drawing_layout` (à arbitrer avec FORGE), `revit_stairs` (écarté, création d'éléments) ; `Session Context` (M3 : équivalent ressource de `get_context`). | R7 | hook client de garde du mainteneur | ADR-026 §2 : RIFT ne compte sur aucun hook client ; la politique de document, le garde lecture et les reçus sont appliqués par l'add-in. La modification du harness se fait dans le vault (`75_Harness/Claude-Code/`), pas depuis ce dépôt. |
| R8 | restes `zenrvt` | L'enregistrement MCP `zenrvt` laissé au niveau de l'ancien dossier du projet dans la configuration du client, et l'ancien dossier de données de l'add-in : suppression à confirmer par le mainteneur (suppression de fichiers, configuration hors dépôt). |
| R9 | multi-version | Le poste n'a que Revit 2026 et pas le SDK .NET 10 : la recette 2025/2027 ne peut pas se faire ici ; à noter dans le README à la tranche 6. |
| R6 | pyRevit non attaché | Action poste du mainteneur (`pyrevit attach master 2026 --installed`) avant toute recette qui prétend tester la coexistence (ADR-019). |
